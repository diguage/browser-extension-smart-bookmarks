# 智能书签访问统计插件 — 设计文档（v2 定稿）

> 目标平台：Chrome + Edge + Firefox（Manifest V3 / WebExtension）
> 状态：设计定稿，决策点已全部确认（见「12. 已确定的决策」），待进入实施。

## 1. 文档说明

v2 相对早期草案的主要变化：

1. 统计口径从「点击次数」改为「被访问次数」，以浏览器历史记录为事实来源。
2. 展示采用双模式：原生书签栏近似重排 + 扩展自绘侧边栏严格展示。
3. 宽度估算从屏幕宽度改为浏览器窗口宽度，并明确「原生栏可见数量不可精确获得」这一边界。
4. 补全 Firefox 兼容方案：后台模型、侧边栏、无 `system.display` 的替代做法。

## 2. 需求与目标

需求：

1. 统计每个收藏链接的访问次数；链接位于 Folder 时，Folder 的访问次数等于其下所有链接访问次数之和，一次访问沿祖先链向上累计到根 Folder。
2. 根据链接 / Folder 的访问次数对书签进行排序展示。
3. 从右向左降序排列：最右侧是访问次数最多的项；根据浏览器窗口大小动态调整展示的链接 / Folder 数量，保证访问最多的项始终可见。

目标：统计口径稳定、排序方向与自适应符合需求、Chrome / Edge / Firefox 三端可维护、尽量降低对用户日常使用书签的干扰。

## 3. 可行性结论

| 需求 | 可行性 | 关键结论 |
| --- | --- | --- |
| 1. 访问统计 | 可行 | 以 `history.onVisited` 为统计来源，覆盖点击、地址栏输入、历史/搜索打开等全部访问方式 |
| 2. 按访问量排序 | 可行 | 原生书签栏可用 `bookmarks.move` 重排；自绘界面可完全控制排序 |
| 3. 右到左 + 窗口自适应 + 最高项始终可见 | 部分可行 | 原生栏是 LTR、右侧先被溢出裁剪，「最右」与「始终可见」在原生栏上无法同时保证；必须由扩展自绘界面承担 |
| Chrome / Edge / Firefox 三端 | 可行 | 共用 MV3 + webextension-polyfill；Edge 属 Chromium 系、基本复用 Chrome 实现，Firefox 的 manifest、后台模型、侧边栏 API 有差异，需构建期处理 |

Safari 首版不支持：其 WebExtension 缺少本方案依赖的 `bookmarks` 与 `history` API，详见 8.4。

**一句话结论**：方案整体可行。统计统一采用「被访问次数」，数据层与聚合逻辑三端一致；展示分两层——原生书签栏做「近似热度重排」（体验好，但不承诺需求 3 的硬保证），扩展自绘侧边栏做「右到左 + 窗口自适应 + 最高项始终可见」的严格实现。

两条关键平台限制：

- 浏览器不开放「原生书签被点击」事件，因此统计「被访问次数」而不是「点击次数」。
- 原生书签栏是 LTR 布局、溢出时右侧先被裁，「最右」与「始终可见」无法同时保证；该硬保证由自绘侧边栏承担。

## 4. 核心统计口径

### 4.1 被访问次数

被访问次数 = 某书签 URL 被浏览器记录进历史的次数。

- 点击书签、地址栏输入、从历史或搜索结果打开、页面内跳转，都会产生一次访问并计入。
- 不区分「用户从哪里来」，衡量的是「这个 URL 被使用得多频繁」，更适合做排序依据。
- 隐身窗口的访问不会被记入历史，因此默认不计入，属隐私友好的自然结果。

### 4.2 相同 URL 合并

相同 URL 的判定（合并键）= 协议 + 域名 + 端口（默认端口归一）+ 路径 + 查询参数，全部一致才视为同一 URL。

- `#fragment` 不参与比较：`a.com/p` 与 `a.com/p#top` 视为同一 URL。
- 查询参数按原顺序比较，不做排序，避免改变语义。

同一 URL 的多个书签在统计上合并为一个实体：

- 计数按 URL 记一次：该 URL 被访问一次，`visits[规范化URL]` 加 1，而不是给每个书签各加 1。
- 这些书签各自展示同一个 URL 级计数，排序时权重相同。
- 任意层级的聚合同样按「不同 URL」去重，一次访问不会因重复收藏被放大。
- 默认只做统计合并，不动书签；物理删除是可选工具，见 5.8。

### 4.3 为什么用 history 而不是 webNavigation

- `history.onVisited` 是浏览器历史记录的事件源，三端都支持，且与「被访问次数」的语义严格一致。
- `webNavigation.onCommitted` 更接近「导航」，但会遗漏聚焦已有标签、重载等场景，且与历史记录口径可能不一致。
- 保留一个可选项：后续若需要「更实时」的 UI 刷新，可额外挂 `webNavigation` 做即时提醒，但计数仍以 `history.onVisited` 为唯一事实来源，避免双计。

## 5. 数据采集与数据层

### 5.1 采集链路

1. 后台单一写者监听 `history.onVisited`。
2. 用内存索引把「URL → 书签 id 列表」映射出来，判断本次访问是否命中某个书签。
3. 命中后对规范化 URL 的计数加 1，写回 `storage.local`，更新该 URL 的最近访问时间。
4. 广播消息通知已打开的 UI 刷新（可选）。

### 5.2 URL 索引与规范化

- 启动时用 `bookmarks.getTree()` 构建 `Map<规范化URL, bookmarkId[]>`。
- 在 `bookmarks.onCreated / onChanged / onMoved / onRemoved / onImportEnded` 时，debounce 后整树重建索引（书签规模下整树重建是 O(n)，简单可靠，优于增量维护）。
- 不使用 `bookmarks.search` 做精确匹配：该接口是「关键词文本查询」，可能过匹配或漏匹配；自建索引可对 URL 规范化做完全控制。
- 规范化规则：去掉 `#fragment`；统一协议大小写；归一默认端口（`http://` 80、`https://` 443）。索引中同时保存「精确 URL」和「规范化 URL」两级键，匹配时先精确后规范化。

### 5.3 写放大与一致性

- 访问是低频行为，逐次写 `storage.local` 可接受；连续访问同一 URL 时做短时间窗合并写（只合并 IO，不合并计数值）。
- 所有计数写集中在后台单一写者，避免多页面读改写竞态。
- 重排、升级、去重等结构性修改也由后台串行执行，设置「执行中」标志防止重入与并发冲突。

### 5.4 存储结构

使用 `storage.local`（本地优先，不依赖网络）：

```ts
interface SmartBookmarksStore {
  schemaVersion: number;              // v2，升级时按版本号惰性迁移
  visits: Record<string, number>;     // key = 规范化 URL（书签 id 仅作展示映射）
  lastVisitedAt: Record<string, number>; // key = 规范化 URL
  moreFolderId?: string;              // 自建「更多」文件夹的节点 id
  settings: {
    reorderNativeBar: boolean;        // 是否重排原生书签栏（默认 true）
    nativeDirection: 'rightHigh' | 'leftHigh'; // 原生栏方向（默认 rightHigh）
    overflowMode: 'browser' | 'customFolder';  // 原生栏溢出（默认 customFolder）
    sortSubfolders: boolean;          // 是否递归排序 Folder 内部（默认 true）
    deduplicateEnabled: boolean;      // 物理去重开关（默认 false，手动执行）
    autoPromoteToBar: boolean;        // 高热度自动升级到书签栏（默认 false）
    promoteThreshold: number;         // 升级阈值：访问次数 >= 此值才升级（默认 30）
    syncEnabled: boolean;             // 跨设备同步开关（默认 false）
    debugSortIntervalMinutes: number; // 开发调试用重排周期（分钟），生产默认 0 = 关闭
    skipIncognito: true;              // 固定为 true（历史天然不计隐身）
  };
}
```

统计范围固定为全部书签；「自动升级到书签栏」负责把其他收藏里的高热项前移到书签栏。

### 5.5 Folder 递归聚合

Folder 计数 = 其子树中全部**不同规范化 URL** 的 `visits` 之和，读取时实时推导，不做沿祖先链的增量写。

- 同一 URL 在该 Folder 子树内出现多份时只计一次，与「相同 URL 合并」规则一致。
- 推导值永不自相矛盾，且书签移动、删除、导入后无需补偿。
- 语义说明：链接被移出 Folder 后，该 Folder 计数随之下降；若产品上要求「Folder 保留历史累计」，那是另一套历史快照语义，第一版不采用。

### 5.6 计数归属

- 计数绑定 URL，不绑定书签 id：链接在 Folder 间移动，URL 计数不变；书签 URL 被修改后，新 URL 使用该 URL 已有的计数。
- 书签 id 只用于「URL → 展示」的映射；`bookmarks.onRemoved` 后若某 URL 不再被任何书签引用，其计数可惰性清理。
- 书签导入导出导致 id 变化不影响统计，因为计数按 URL 保存，导入后同 URL 书签直接恢复原计数。

### 5.7 跨设备同步（可选，默认关闭）

- 直接使用浏览器内置的 `storage.sync`（Chrome 登录 Google 账号、Firefox 登录 Firefox 账号后自动跨设备同步），不搭建任何中转服务；未登录时 `storage.sync` 退化为本地存储，不报错。
- `storage.local` 仍作为实时写入点，每条访问照常写本地；`storage.sync` 只做「定期批量快照 + 启动时合并」，避免触发写入限流（总量约 100KB、单 key 约 8KB、条目数约 512，并有每分钟 / 每小时写入上限，具体以官方文档为准）。
- 合并策略：跨设备按 URL 将计数相加、`lastVisitedAt` 取较新值；极端并发下允许细微偏差。
- 开关默认关闭，开启后仅同步计数与设置，不同步完整访问历史。

### 5.8 物理去重（可选，默认关闭）

- 目的：把指向同一完整 URL 的多份书签合并为一份，减少冗余。
- 默认关闭：关闭状态下不删除任何书签，仅按 4.2 做统计合并。
- 触发方式：设置页提供「物理去重」工具；执行前先生成预览（列出保留项与将删除项），用户确认后才删除，并建议先导出书签备份。
- 保留规则：同一 URL 的重复集合中，保留「最常用位置」的那一份。「最常用位置」指书签栏（工具栏）：若重复集合中存在位于书签栏内的书签，保留书签栏内树中先出现的一份；若都不在书签栏，保留树中先出现的一份；其余重复项删除。
- 安全约束：只删除链接节点，不删除 Folder；每个 URL 至少保留一份；只删除确认属于「重复 URL」的节点。
- 执行后：剩余书签自动沿用该 URL 的计数，因为计数按 URL 保存，无需迁移。

## 6. 展示与排序

### 6.1 排序键与作用范围

- 排序键：访问次数降序 → 最近访问降序 → 标题字典序；Folder 与链接同场参与排序，Folder 权重为聚合值。
- 递归规则：任意层级的直接子项都按同一排序键混合排序；Folder 展开后递归应用同一规则，默认开启，可在设置中关闭（`sortSubfolders`）。
- 书签栏定位：Chrome 书签栏根节点 id 为 `1`，Firefox 工具栏根节点 id 为 `toolbar_____`；实现时通过 `bookmarks.getTree()` 的根节点子项识别（按约定 id 或标题），不可硬编码单一值。
- 作用范围：统计覆盖全部书签；模式 A 的物理重排默认只作用于「书签栏」子树（含其内部所有层级），不自动改动「其他书签」等顶层子树；模式 B 侧边栏可展示全部书签而不移动真实书签。

### 6.2 模式 A：原生书签栏近似重排（默认开启）

通过 `bookmarks.move` 直接重排原生书签栏。

方向策略（默认 `rightHigh`）：

- `rightHigh`「最高在最右」：对排序结果 reverse 后落位，视觉上最高项在最右，贴合需求 3 的方向。
  - 已知代价：原生栏 LTR、溢出时右侧先被收进 `>>`，窗口偏窄或估算偏大时，最高项反而最先被裁；此模式只承诺「排序」，不承诺「始终可见」。
- `leftHigh`「最高在最左」：最高项落在 index 0，原生栏从右裁剪，因此最高项始终可见；但方向与需求 3 相反，作为备选保留。

溢出策略（默认 `customFolder`）：

- `customFolder`：自建「更多」文件夹收纳放不下的项。书签栏本身仍按 `rightHigh` 展示，放不下的项进入该文件夹，内部按热度降序排列（最热在顶部）。
  - 该文件夹放在书签栏最右侧；内部顺序由扩展完全控制，从而同时满足「书签栏最高在右」和「溢出区内从上到下热度倒序」。
  - 首次创建时使用固定标题并记录其 id（`moreFolderId`）；若用户已有同名文件夹则复用或提示，避免重复创建。
  - 代价：溢出不是原生 `>>`，且会把书签移入该文件夹，改变用户组织结构。
- `browser`：只重排书签栏内已有项，溢出交给浏览器原生 `>>`，侵入最小；但原生 `>>` 内部顺序不可控，`rightHigh` 下为热度升序，作为备选保留。

### 6.3 模式 B：扩展自绘侧边栏（需求 3 的严格实现）

这是唯一能同时满足「从右向左」与「最高项始终可见」的表面：自绘界面同时控制排序方向、裁剪方向和真实容器宽度。

- 布局：`flex-direction: row-reverse`，列表第 1 名永远渲染在最右侧槽位。不用 CSS `direction: rtl`，避免 URL 文本与标点被镜像。
- 自适应：`ResizeObserver` 监听容器真实宽度；每次变化后按排序结果贪心放入最多 N 项，直到放不下，其余项折叠进左侧「更多 N+」按钮。
- 裁剪发生在左侧（低访问侧），右侧最高项无论窗口多窄都保持可见，满足需求 3。
- Folder 与链接同场排序；展开 Folder 后递归应用同一布局。
- 主形态：Chrome 用 `sidePanel`（Chrome 114+，通过 `sidePanel.setPanelBehavior({ openPanelOnActionClick: true })` 绑定工具栏图标）；Firefox 用 `sidebar_action`。
  - 注意：Firefox 侧边栏默认在浏览器左侧，与「鼠标在右」不完全一致；需在 spike 阶段确认是否可接受 / 可右置，否则退化为弹窗或新标签页。

### 6.4 自动升级到书签栏（可选，默认关闭）

- 前提：Chrome / Edge / Firefox 中「书签栏」与「其他书签 / 收藏」是分开的顶层子树，因此需要该配置。若目标环境两者不区分，则排序已自动把高热项放到前面，无需此功能。
- 规则：统计范围覆盖全部书签。每次执行重排时，对不在书签栏中的链接节点，若其访问次数 ≥ `promoteThreshold`（默认 30，按 1920×1080 常见屏幕可放书签数约 12–15 个的两倍估算），将其移动到书签栏，随后按 6.2 的排序与方向策略落入对应位置。
- 约束：只移动链接节点，不移动 Folder；已在书签栏内的节点不重复移动；目标 URL 若已存在于书签栏则跳过（交由相同 URL 合并 / 物理去重处理）。
- 只升级、不自动降级；移动记录写入日志，便于用户查看与撤销。

### 6.5 重排调度

- 生产环境：每天只重排一次，在当天第一次使用浏览器时触发——扩展启动 / 被唤醒时检查 `lastSortDate != today`，是则执行一次重排并记录当天日期，否则跳过。
- 目的：降低对用户的干扰，避免书签在用户操作期间被突然移动。
- 手动入口：设置页 / 弹窗提供「立即排序」，随时可手动触发，不受日调度限制。
- 开发 / 调试：通过 `debugSortIntervalMinutes` 把周期缩短到每 1 或 5 分钟执行一次（生产默认 0 = 关闭），用 `chrome.alarms` 短周期驱动，便于快速验证。
- 并发守卫：日调度与手动触发共用同一「执行中」标志，避免重叠执行。
- 自适应说明：侧边栏（模式 B）的实时布局不受此限制，因为它只调整自绘界面，不移动真实书签；模式 A 的物理重排严格按上述调度执行。

## 7. 宽度与自适应算法

### 7.1 原生栏（模式 A）

- 用 `chrome.windows.getLastFocused()` 的窗口宽度（DIP）替代 `system.display` 的屏幕宽度。
- 可用宽度 = 窗口宽度 − 浏览器 UI / 工具栏 / 溢出按钮的预估预留（设置页可调）− 安全余量。
- 单项宽度 = 图标宽 + 间距 + 标题实测宽 + 左右 padding；标题为空或极短时取最小宽度（仅图标 + padding）。
- 标题宽度用离屏 Canvas `measureText` 按近似字体测量，替代硬编码字符宽度；设置最大标题显示宽度，超长标题按「…」截断后再参与计算，避免个别长标题占满整栏。字体指标与原生栏不可能完全一致，只能逼近。
- 窗口宽度在每次执行重排时读取；不在窗口缩放时实时重排（调度见 6.5），避免打扰用户。
- 明确边界：浏览器原生栏「恰好放得下几项」的阈值是内部渲染行为，没有 API 能拿到精确值；模式 A 的可见数量只能是逼近，这是它不承诺需求 3 的根本原因。

### 7.2 自绘侧边栏（模式 B）

- `ResizeObserver` 拿到真实容器像素宽度，配合 `measureText` 或 `getBoundingClientRect` 的实测项宽，可精确计算可见数量，不存在原生栏的黑盒问题。
- 项宽同样按「图标 + 标题实测宽 + padding」计算：标题为空或极短时取最小图标宽，超长标题截断为「…」；优先用渲染后的 `getBoundingClientRect` 实测，标题变化时重测。
- 裁剪方向固定为「左侧折叠」，因此「最高项在右且始终可见」是确定性保证。

## 8. 跨浏览器架构

### 8.1 技术栈

- 构建工具：Vite（当前前端 / 扩展领域流行度与用户量最高的构建工具，底层用 esbuild / Rollup 加速）。
- 扩展框架：wxt（构建在 Vite 之上、面向浏览器扩展的现代框架），按 target 生成 Chrome / Edge / Firefox 多套产物，自动处理三端 manifest 差异。
- 语言与兼容层：TypeScript + `webextension-polyfill`（统一 `browser.*` / `chrome.*`）。

### 8.2 三端差异

| 项 | Chrome MV3 | Edge（Chromium MV3） | Firefox MV3 |
| --- | --- | --- | --- |
| 后台模型 | Service Worker | Service Worker | Event Page（`background.scripts`，不支持 service_worker） |
| 命名空间 | `chrome.*` | `chrome.*` | `browser.*`（Promise） |
| 书签栏根节点 | 约定 id `1` | 约定 id `1` | 约定 id `toolbar_____` |
| 侧边栏 | `sidePanel`（默认右侧） | `sidePanel`（需验证目标版本支持） | `sidebar_action`（默认左侧，需验证 MV3 支持与右置方案） |
| 工具栏按钮 | `action` | `action` | `action`（Firefox 109+） |
| 屏幕 API | `system.display` 可用 | `system.display` 可用 | 无 `system.display`，改用 `windows` API |
| 历史 API | `history.onVisited` 可用 | `history.onVisited` 可用 | `history.onVisited` 可用 |
| 同步账号 | Google 账号 | Microsoft 账号 | Firefox 账号 |

Edge 属 Chromium 系，代码基本与 Chrome 共用；落地前重点验证 `sidePanel` 在目标 Edge 版本的支持情况，发布走 Microsoft Edge 加载项商店或本地侧载。

### 8.3 模块划分

- `manifest`：三端变体，构建期生成
- `background`：历史监听、URL 索引、访问计数存储、聚合计算、原生栏重排、窗口宽度估算、重排调度、书签事件监听
- `sidepanel`：自绘侧边栏，右到左自适应布局
- `popup`：快捷视图（统计 TOP N、手动重排、清空）
- `options`：设置页（方向 / 溢出 / 同步 / 物理去重预览与确认、导出 / 清除）
- `lib`：URL 规范化、宽度测量、聚合算法、存储封装

### 8.4 Safari 说明（首版不支持）

- Safari 的 WebExtension 目前不提供 `bookmarks` 与 `history` API，而本方案的「访问统计」和「原生书签栏重排」分别依赖这两个 API，因此无法按现有设计在 Safari 上实现。
- wxt 可以产出 Safari 的 Xcode 工程，但打包只解决构建，不解决 API 缺失；它让「未来 Apple 开放 API 后」的移植成本更低，不代表现在能跑。
- 备选路径（不同产品形态）：Safari 端只做「扩展自管理收藏夹」，由扩展自己保存链接并在自绘界面内点击计数；它读不到、也重排不了 Safari 原生书签。
- 决策：首版目标定为 Chrome / Edge / Firefox；若 Apple 后续开放 `bookmarks` / `history` API，再评估 Safari 移植。

## 9. 权限与隐私

最小权限集：

- `bookmarks`：读写书签（重排、索引、去重与升级）。
- `storage`：保存访问计数与设置。
- `history`：访问统计的事实来源（能力较强，需在安装说明中说明用途）。
- `alarms`：重排调度（生产每日一次，开发期 1–5 分钟短周期）。
- Chrome / Edge 侧 `sidePanel` 权限；Firefox 无对应权限，仅 `sidebar_action` manifest 键。
- `windows` API 无需额外权限。

隐私建议：

- 仅保存「URL → 计数」，不保存原始访问记录、不保存完整 URL 历史。
- 默认只存本地；跨设备同步为可选开关（默认关闭），开启后按 5.7 的批量快照与合并策略走 `storage.sync`。
- 隐身窗口访问天然不计入。
- 提供「导出 JSON」「清空全部统计」。

## 10. 边界与风险清单

- `history.onVisited` 异步触发，可能有短暂延迟，UI 不保证实时。
- 相同 URL 合并后，`#fragment` 不参与比较（已确定）。
- 重定向链中的中间 URL 若命中书签也会计入；可接受，文档注明。
- URL 规范化（fragment、尾斜杠、大小写、默认端口、查询参数的大小写与编码）是匹配准确性的主要工作点。
- 物理去重是破坏性操作：必须预览 + 用户确认 + 建议先备份，且只删链接节点、每个 URL 至少保留一份。
- 自动升级到书签栏会移动书签结构：默认关闭，只移动链接节点、不自动降级，并记录移动日志。
- 自建「更多」文件夹模式会把书签栏中放不下的项移入该文件夹，改变用户组织结构；首次启用需提示，并尽量保留原始顺序以便关闭后还原。
- 原生栏「最高最右」与「始终可见」无法同时满足，方向策略二选一。
- 原生栏精确可见数量不可得，模式 A 只能逼近。
- Firefox `sidebar_action` 的 MV3 支持、侧边栏左侧布局与「鼠标在右」的落差，需落地前实测。
- Edge `sidePanel` 在目标版本的支持情况、加载项商店的发布与权限审核差异，需落地前实测。
- 书签导入导出：计数按 URL 保存，同 URL 书签导入后可恢复计数；URL 被改写的书签无法追溯。
- service worker / event page 被回收：索引可重建，计数以 `storage.local` 为唯一事实来源。
- 自动重排会覆盖用户手工整理的书签栏顺序；需提供开关，并在首次启用时明确提示。

## 11. 实施步骤建议

1. **Spike（半天）**：三端最小可安装骨架，验证 MV3、后台模型、`sidePanel` / `sidebar_action`、polyfill、`history.onVisited`、书签栏根节点定位。
2. **数据层**：URL 索引、计数存储、聚合算法、书签事件监听与清理、schema 迁移。
3. **原生栏重排**：窗口宽度估算、方向与溢出策略、每日一次调度 + 开发短周期、手动触发入口。
4. **自绘侧边栏**：排序渲染、`row-reverse`、`ResizeObserver` 自适应、Folder 递归展开。
5. **popup 与 options**：统计视图、设置、物理去重预览与确认、导出 / 清除。
6. **测试**：Chrome stable + Edge stable + Firefox stable，覆盖多书签同 URL、书签移动 / 删除 / 导入、窗口缩放、大批量书签、日调度与手动触发并发场景。

## 12. 已确定的决策

1. 相同完整 URL 在统计上合并为一个实体；`#fragment` 不参与比较。
2. 原生栏方向默认 `rightHigh`（最高在最右，接受可见性风险），先试效果再评估是否引入 `leftHigh`。
3. 溢出采用自建「更多」文件夹（`customFolder`）——书签栏 `rightHigh`，文件夹内部热度降序（最热在顶部）；原生 `>>` 作为备选保留。
4. 统计范围 = 全部书签；「高热度自动升级到书签栏」默认关闭；`promoteThreshold` 默认 30（可在设置中调整）。
5. 主界面采用侧边栏（Chrome / Edge `sidePanel`，Firefox `sidebar_action`），弹窗仅作快捷操作入口。
6. 提供跨设备同步开关（`storage.sync`），默认关闭；实时写入仍在 `storage.local`，同步走定期批量快照 + 启动时合并。
7. 物理去重默认关闭、手动执行；「最常用位置」= 书签栏（工具栏），重复集合优先保留书签栏内的一份，其余删除。
8. 原生栏物理重排每天一次（当天首次使用浏览器时执行），开发期可用 1–5 分钟调试周期。
9. 支持 Microsoft Edge：属 Chromium 系，复用 Chrome 实现；落地前验证 `sidePanel` 版本支持与商店发布。
10. Safari 首版不支持（缺少 `bookmarks` / `history` API）；若 Apple 后续开放 API 再评估，或提供独立的「扩展自管理收藏夹」作为备选形态。
